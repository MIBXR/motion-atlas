# 决定 1：实时播放的绘制（批准）

1. 每个宿主 `requestAnimationFrame` 回调里，先求出目标步：`k_target = floor(墙钟累计时间 × 60)`。
2. 用 `__filmSkipRender = true` 逐步推进到 `k_target − 1`。所有 60Hz 的状态步与输入派发照常执行。
3. 关闭跳过，执行第 `k_target` 步，只绘制这一步。
4. 若某一帧要推进的步数超过 30 步（0.5s），也照样全部推进完，不丢步。
5. 暂停时立即停止，不再排队追赶。暂停后读到的胶片时刻必须等于外层时间轴的时刻。

seek、离线导出、render 模式的逐帧绘制不变。

## 验收

- 从 F21.5、F40、F60 三处各实际播放 5s，然后暂停。每次记录外层时刻与 iframe 时钟时刻：两者之差 ≤ 1/60s；墙钟 5s 对应的胶片推进量在 4.9–5.1s 之间。横竖都测。
- 每次暂停后，seek 回同一时刻，DOM 状态一致、画布缩略 MAD < 2/255。

# 决定 2：时钟对齐的原版对照（批准）

1. 原版对照副本**不改源码**。用 Playwright 的 `addInitScript`（或在副本的 index.html 最前面临时注入一个 script 标签，测完恢复）注入与移植版**完全相同**的 `clock-shim.js`：相同的 60Hz 步长、相同的 `Date` 纪元、相同的 `Math.random` 种子。
2. 两边用同一张动作表，在同样的步数派发同样的输入；原版一侧不加 `?film=1`。
   - 若原版必须点击进入页才开始开场，把点击放在第 0 步之前，并记录这一偏移。
   - 把两边对齐到“开场第一帧”这一步。
3. 在原 §9.1 的 17 个时刻 × 横竖 2 种画幅上，取同一步号截图，输出新对照图到 `dev/shots/T5r/parity-aligned/<orient>-<F>.png`，并计算缩略 MAD。
4. 逐张查看。
   - 对不上的，要定位到代码层面的原因：具体文件 / 行，以及两边的状态差异。
   - 如果是移植改动造成的（clock-shim、跳过渲染门控、film 入口、音频重构、路径、画质参数），就修好，再重测。
   - 如果确认是上游本身的非确定因素（例如异步解码完成时机），写明证据，保留差异。
5. 原来的 34 张实时对照图保留，并在报告中标注为“实时参考，存在相位差”。
