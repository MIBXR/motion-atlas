## 一、这一轮要解决什么

用户反馈（2026-10-15）归纳为五类：

1. **精致度**：案例与巧思像半成品，细节不够。每个都要逐项打磨到“可以直接拿去用”的程度，不偷工减料。
2. **固定画幅**：放弃舞台内部的自适应排版。每个 Demo 只有两种画幅：横屏 **1920×1080** 与竖屏 **1080×1920**，各用一套按像素设计的构图，整体等比缩放显示。由此消除缩放时的遮挡（文字被线条压住）与错位（路线、节点圆点、连线没对齐）。
3. **预加载**：地图大范围移动时瓦片来不及加载。所有异步资源（地图瓦片、图片、字体）在播放前预取并缓存，播放到某一帧时数据必须已经就绪。
4. **声音**：每个案例与巧思都要有声音设计。节拍与音效是动效的组成部分，不是附加项。
5. **站点与实验室**：详情页舞台过大、时间轴要滚动才看得到；暂停按钮有时点不动；节奏实验室的声音单薄、偏慢；“拍点与吸附”的偏移、细分差异听不出也看不出。

另有两条点名问题：

- **地图巡礼**：元素未对齐；观感朴素；大范围移动卡瓦片。
- **档案终端**：相对 RhineLabUI 原仓库简化过度：档案之间的循环与上下左右切换及过渡缺失；开场图标从无线信号变成了两个圆圈。

## 二、全局约定（所有子任务必须遵守）

### 2.1 舞台

- 舞台尺寸固定：`landscape` 1920×1080、`portrait` 1080×1920。舞台内部一律使用舞台像素坐标，不使用 `vw/vh/%/clamp()` 或媒体查询改变布局。
- 舞台作为一个整体按 `contain` 等比缩放到容器中，四周留黑边（letterbox）；缩放只发生在舞台根节点上。
- 横竖两种画幅是**两套构图**，不是同一套元素的重排：竖屏按手机竖屏视频的观看方式重新安排信息层级、字号与镜头。
- 画幅选择：URL `?orient=landscape|portrait`；未指定时由宿主决定（站点详情页的切换按钮），独立打开时按窗口宽高比自动选择。运行时切换画幅要立即重排并保持当前时刻。
- 渲染：`render.mjs --orient portrait` 输出 1080×1920，`--orient landscape`（默认）输出 1920×1080，DPR 1。
- 实现方式由基础子任务（T1）在 `kit/motion-kit.js` 中提供统一的 `MotionKit.stage()`，并写进 `docs/pipeline.md`。

### 2.2 字号

用户约束是“最终渲染字号 ≥ 12px”。固定画幅整体缩放后，舞台字号必须按常见观看尺寸换算：

- 横屏舞台最小字号 **24px**（在 ≥ 960px 宽的显示尺寸下 ≥ 12px）。
- 竖屏舞台最小字号 **36px**（在 390px 宽的手机上约 13px）。
- 站点里的缩略预览（卡片封面、小尺寸嵌入）属于缩放预览，不受此限；详情页的默认显示尺寸要保证横屏舞台宽度 ≥ 960px（桌面）。
- `check.mjs` 相应改为：Demo 内按舞台字号下限检查，站点页面仍按 12px 检查。

### 2.3 对齐与遮挡

- 几何元素（路线、节点、连线、刻度、框线）由同一套坐标函数计算，端点与圆心严格重合；描边按整数或半像素对齐，避免发虚。
- 文字永不被线条或图形压住：建立明确的层级（背景 → 图形 → 文字 → HUD），文字底部加衬底或给线条留出避让间隙。
- 每个子任务交付前，在每个节拍点截取横竖两张图，逐张检查对齐与遮挡。

### 2.4 声音

- 统一由 kit 中的声音引擎合成（WebAudio），零外部素材，避免版权与下载问题；需要更丰富的质感时用合成手段解决（噪声塑形、FM、包络、卷积混响、侧链压缩）。
- 时间驱动作品：声音写成**乐谱**——一组 `{t, voice, params}` 事件（可由函数按拍生成），由引擎在播放时按前瞻调度；拖动、跳拍、暂停时立即停止已排程的声音，从新位置继续。同一份乐谱可用 `OfflineAudioContext` 离线渲染成 WAV，`render.mjs --audio` 与画面一起导出（有 ffmpeg 时合成到 MP4）。
- 交互作品：输入即时触发反馈音；自动驾驶演示时同样从乐谱出声。
- 每个案例至少包含：节拍底或环境底（适用时）+ 关键事件音（转场、命中、确认、揭示、收尾）+ 细节音（打字、刻度、悬停）。每个巧思至少有它自己的触发音。
- 默认静音，站点详情页提供显眼的声音开关；音量适中，主混音有限幅，避免爆音。

### 2.5 预加载

- Demo 在 `__motion` 就绪前完成必要资源的预取；地图类按全部相机关键帧（含飞行途中的采样点）预取各缩放级别的瓦片并保留缓存；播放中仍未就绪时，渲染模式下等待、实时模式下降级（淡入）而不是闪白。
- 暴露预加载进度，站点可显示加载状态。

### 2.6 细节质量

- 参考作品逐帧对照：有参考视频或开源源码的案例，先列“原作有、我们没有”的清单，逐项补齐或说明不做的理由。
- 交互：上下左右、滚轮、拖拽、键盘都要有对应的过渡，不允许瞬切；空闲态有呼吸。
- 减少动态、12px／舞台字号、SVG 图标、版权约束保持不变。

### T4 补充要求（用户 2026-10-15）

当前路线使用北京、杭州、上海。OpenFreeMap 的矢量瓦片来自 OpenStreetMap，这些城市的建筑、POI 等数据不完整，部分区域只剩平面底图，3D 建筑时有时无，观感不一致。改为**日本**路线：

- 日本的 OSM 数据（建筑轮廓、铁路、水系、地名）完整度高，原参考视频本身也是日本旅行（关西、京都等）。

## 四、每个子任务的固定流程

1. **调研**（动手前完成，写进交付报告）
   - 通读该案例现有的全部代码、条目 JSON、研究笔记、所属巧思。
   - 对照参考：有参考视频的用 `scripts/frames.mjs` 取帧；有开源仓库的读源码；游戏类读研究笔记中的公开资料。
   - 对当前 Demo 在每个节拍点截图（横屏 1920×1080），列出问题清单：对齐、遮挡、缺失的动效与交互、观感单薄之处、性能与加载。
2. **设计**：横竖两套构图说明、节拍表（必要时调整）、声音表（每个事件对应的音色与时刻）、对齐规则。
3. **实现**：只改本子任务范围内的文件（见各任务说明）；共享文件（kit、站点、scripts）只有 T1–T3 和 T13 可以改，其他子任务需要新能力时写进报告，由主任务决定。
4. **验证**：
   - 横竖两种画幅在每个节拍点截图并逐张检查；交互作品额外截取每种输入的过程帧。
   - `node scripts/smoke.mjs --only <ids>` 通过（两种画幅）。
   - 舞台字号下限、SVG 图标、减少动态逐项确认。
   - 声音：在浏览器中实际播放检查触发时刻；用离线渲染导出 WAV 检查是否爆音、是否与画面对齐。
5. **更新资料**：条目 JSON（节拍、Token、Prompt、视频 Prompt、迁移字段、声音说明）、研究笔记的“验证记录”。
6. **交付报告**：做了什么、问题清单逐项的处理结果、截图清单、遗留问题。

## 五、执行与审核

- 每个子任务由一个独立的子 Agent 执行（新上下文，避免长任务注意力涣散），按 T1 → T13 顺序一个一个来。
- 主任务对每个交付做审核：读报告、看截图（横竖每个节拍点）、抽查代码、跑冒烟与检查；不达标就打回补做。审核通过后提交到 `feat/polish-round-1` 并推送分支，便于随时查看进度。
- 全部完成后由主任务做 T13 整合审核，开一个 PR，由用户合并。
