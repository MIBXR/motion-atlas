- 参考：【眩晕瘫坐 旅游时拍的素材给Opus5.5剪出来是这样】（哔哩哔哩，<https://b23.tv/eBjaN0O>），画面署名 @DWTornier

## 一句话结构

一个稳定的**世界层**（地图）+ 一套持续更新的**信息层**（四角 HUD）+ 有节制的**模式切换**（卡片 / 全屏实拍 / 全屏动画回忆 / 分屏对比）。地图永远是底座，HUD 永远在报时；只有高光才允许离开地图，而离开时 HUD 也跟着走。

## 节奏分析

- **事件密度**：地图段落平均每 4–6 秒出现一个新事件（新卡片、新地名、计数、便签、歌词换行），观众始终有新信息可看，但同一时刻只有一个主事件。
- **模式切换**：约每 10–15 秒离开一次地图（全屏实拍/动画/对比），全屏段落持续 1.2–7 秒；回到地图后至少留 1–2 秒“呼吸”。
- **能量曲线**：开场低 → 片名第一峰 → 旅程中速 → 回忆与对比为最高峰 → 意外事件制造第二个尖峰 → 结尾回落。Demo 的能量曲线按同样形状设计（见条目 `energy`）。
- **一致性来源**：所有模式共用 HUD、颗粒与强调色系统，所以“切换”像在同一个系统里切视图，而不是不同素材的拼接。

## 预取与缓冲（实时播放）

全片 60 秒的镜头（含飞行途中）按视频播放器方式做渐进缓冲，不在起播前全部下载。当前横屏计划 725 块瓦片；竖屏尚未按地球远景 5ms 采样策略复测。完整字节分析只覆盖独立的 1288 点版本，不能作为当前精确体量。实现见 `script.js` 的“缓冲（实时模式）”一节：

1. **扫描**：开始播放前把全片镜头按时间采样（缩放 0.12 级 / 平移横 150px、竖 100px / 俯仰 2.5° / 方位 3° 变化即记一个点，缓慢段间隔最多 0.2s）；快速推拉在 zoom<6 的地球远景每 5ms 采样，其余快速段每 25ms 采样，跨整数缩放的一格细分 6 份。每个采样点 `jumpTo` 后让 MapLibre 计算所需瓦片（不下载），记录“最早 / 最晚用到的时刻”。最晚时刻为下一采样点、末段为全片结尾，覆盖镜头静止的整段时间。当前横屏 932 点，实测扫描 1621ms；竖屏新策略未复测。
2. **分级**：只在快速推拉帧（缩放 > 1 级/秒）里用到、且有“必需”的上级瓦片可以顶替（一般 3 级以内，世界尺度 z ≤ 5 放宽到 4 级）的瓦片是“可选”的。当前横屏必需 292 块、可选 433 块。上级瓦片在快速镜头中提供过渡画面。
3. **两级缓冲**：下载窗口 45 秒（普通 fetch 拉进浏览器 HTTP 缓存，不占 JS 堆）+ 解析窗口 10 秒（交给 MapLibre 的 worker 解析，放进它的瓦片缓存）。已解析瓦片在主线程堆上约为 pbf 原始字节的 8–10 倍（`tools/tileprobe.mjs`：伏见稻荷时刻缓存 27MB 原始字节 → 清空后堆少 209MB），所以不在画面上的已解析瓦片按原始字节设预算 20MB（`navigator.deviceMemory` ≤ 4 的设备 10MB），超出时只解析 5 秒以内的，淘汰窗口也收紧。
4. **带宽分配**：近期必需（解析窗口内）> 远处必需（只下载）> 可选（20 秒内的必需全部到手之后）。MapLibre 自己为画面发出的可选瓦片请求在带宽紧张时推迟（它们下载一半就会因离开画面被取消，白占带宽）。
5. **播放控制**：`bufferedUntil` = 从播放头起所有采样点瓦片都就绪的最远时刻；前方不足 0.5 秒时停在当前帧并显示舞台内的 “BUFFERING MAP xx%”，攒够 4 秒自动继续；拖动到未缓冲的位置同理。开头 6 秒就绪即开播（加载进度按 `motion:loading` 报给站点）。
6. **渲染模式**（`?render=1`）不走实时缓冲，seek 等待瓦片与地图 idle。原生参数实测 `dev/shots/T4/smoke-fix1-native.json`：横 1920×1080、竖 1080×1920 均为 scale=1、pixelRatio=1、AA 开启、`measureWaitFrames=6`，不应用缩小软件预览的 AA 与精度读回设置。

地球远景的密采样依据是实际缺帧：`dev/shots/T4/live/live-landscape-mirror-small-50mbps-smoke-fix1.json` 在 t=8.51s 记录 `openmaptiles/19w66 z6 unplanned`。`smoke-fix1-scan-wide.log` 的密扫描只在 8.415s 命中该瓦片，相邻原采样点 8.400 / 8.425s 均不命中；`smoke-fix1-camera.log` 记录命中时镜头 zoom=5.899276。当前仅为 zoom<6 的快速段使用 5ms，避免扩大其他镜头的扫描成本。

### 缓冲实测

本机浏览器经系统代理访问 OpenFreeMap 极慢且不稳定（32 块 z14 瓦片浏览器用了 268 秒，而 node 直连 4.5 秒），测出来的是代理而不是 Demo。所以冷缓存实测一律走本地瓦片镜像 `dev/shots/T4/tools/tileproxy.mjs`：第一次从源站取回存盘（`dev/shots/T4/tilecache`），之后按设定的带宽（全局令牌桶）与 40ms 首字节延迟发送；Demo 用 `?tilemirror=http://localhost:4330&demmirror=http://127.0.0.1:4330`（矢量与高程分属两个主机，与线上一样各用各的连接数——放在同一主机时 HTTP/1.1 的 6 个连接会把高程请求饿死，测得的暂停比实际长）。每次新建浏览器配置（冷缓存），视口 640×360 / 360×640，无头 Edge（软件渲染），`tools/live.mjs` 每 200ms 采样一次，全程自动播放到结束。

### 无头软件渲染的播放成本

`smoke.mjs` 使用 `render=1`。该模式不扫描实时缓冲计划，`updateStall()` 直接返回；播放探针中的 `samples=0`、`stalled=false`、`blocking=null`、`states={}` 表示没有缓冲暂停，不能用 `bufferedUntil=0` 推断它在等缓冲。`seek()` 会等待渲染 Promise，但 timeline 的播放 RAF 只调用 `draw()`，不等待返回的 Promise；每次 RAF 的时间增量封顶 0.1s。因此浏览器出现数百毫秒的调度空档时，时间轴最多前进 0.1s，可出现 `playing=true`、无缓冲暂停而 1.5s 检查推进不足的情况。

本机无头软件 GL 由 SwiftShader 实现。诊断文件 `dev/shots/T4/smoke-fix1-probe-variants.json` 中，基线横屏推进 0.2167s、竖屏 0.4668s，均未超过 smoke 的 0.5s 阈值；竖屏记录一次 `getBufferSubData` 同步读回 448.5ms，对应 484ms 长任务。横屏记录 1539ms 的播放回调空档，但窗口内没有读回，说明重复精度读回是已观察到的阻塞来源之一，不能解释全部慢帧。单独冻结读回时横 / 竖推进 0.6166 / 0.6000s，单独关闭 MSAA 时为 0.8000 / 1.1000s；这些单轮对照支持减少软件预览成本，不构成稳定帧率或可相加的性能增益保证。

上述 variants 的 Profiler 从全程快速 sweep 前开始，`top` 汇总包含 sweep，不是纯播放窗口的主线程耗时排名。播放窗口的回调、读回和长任务另按探针 `start` 筛选；没有 GPU 进程 trace，不能据此分摊 GPU、驱动、合成与 JS 的具体占比，也不能把 `avoidZones` 等 profile top 直接认定为播放检查的主要瓶颈。

当前实现：

1. 地图初始化先独立执行 `MAP.softGL = softwareGL()`，不受 `P.render` 的布尔短路影响。`softwarePreview = MAP.softGL && (!P.render || stage.scale < 1)`：软件 GL 的实时模式与缩小 render 预览关闭 MSAA，原生尺寸逐帧 render 保留抗锯齿。
2. 软件预览通过地图 `render` 事件，在地球精度首测完成（`_lastReadbackFrame >= 0`）后设置 `_measureWaitFrames=Infinity` 并解绑监听，保留首测结果、停止重复同步读回。原生尺寸逐帧 render 不进入该分支。
3. 舞台的 9 个主题 CSS 变量通过既有 `sty()` 缓存写入，只在值变化时调用 `setProperty()`。节点文字避让的 DOM 测量在该次渲染遇到首个可见节点时进行，不为没有可见节点的镜头提前测量；UI 逻辑仍逐次执行，每次 seek 都更新。
4. 颗粒使用独立合成层，只更新 transform；未出场路线在出场前 0.6s 以前不可见，不参与覆盖瓦片计算。

轻量探针 `dev/shots/T4/smoke-fix1-probe-lean.json` 不启用 Profiler，也不逐帧读取缓冲快照。当前渲染实现横屏推进 0.8172s、竖屏 1.0507s；观察区间分别 1539.4 / 1574.8ms，两者记录读回 0 次、长任务 0 次，AA 关闭、pixelRatio=2/3，实时缓冲状态均为 `samples=0`、`stalled=false`。这是一次轻量诊断，不是精确 FPS 测量，也不替代完整 smoke；同一最终代码的串行完整验收以 `dev/reports/T4a.md` 4.2 为准。

画幅 roundtrip 的单个 30s 脚本串行等待 `seek(30)`、切到另一画幅、切回，每步都进入渲染等待。本机系统代理参与的远端瓦片等待可使该脚本超时；测试浏览器直连和镜像用于分离网络因素。直连配置本身不能解决软件 GL 的播放推进不足，网络等待与渲染成本需要分别验证。当前生产代码没有本机代理配置，完整检查阈值与超时保持项目原值。
